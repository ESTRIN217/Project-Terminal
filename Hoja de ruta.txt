[P1] Integración completa del bypass W^X (libtermux_exec)
  - Estado: Corregido — LD_PRELOAD eliminado del entorno inicial por
    conflicto con PRoot (exit code 255). Ver [FIX] abajo.
  - Descripción: libtermux_exec.so ahora se copia automáticamente desde el
    nativeLibraryDir a /data/data/.../lib/ al iniciar TerminalService,
    asegurando que LD_PRELOAD=/data_priv/lib/libtermux_exec.so funcione
    correctamente vía el bind mount de PRoot. Se agregó detección de ELF
    class para seleccionar el linker adecuado (32/64-bit). Se mejoró la
    exclusión de rutas Android en el wrapper execve().
  - Logros:
    * NativeLibInstaller.ensureTermuxExecLib() copia la lib al dataDir.
    * termux_exec.cpp: get_elf_class() detecta ELFCLASS32→/system/bin/linker
      y ELFCLASS64→/system/bin/linker64.
    * is_under_proot_rootfs() excluye /system/, /apex/, /dev/, /proc/,
      /sys/, /data_priv/ (solo intercepta rootfs Debian).
    * TerminalService.onCreate() despliega la lib antes de crear sesiones.

  - [FIX] Conflicto LD_PRELOAD + PRoot (exit 255):
    * Problema ORIGINAL: Se asumió que libtermux_exec.so hookeaba execve()
      y rompía PRoot. Pero el exit code 255 persiste incluso sin LD_PRELOAD.
    * Causa real (pendiente de confirmar con logs nativos):
      El exit code 255 puede originarse en termux.cpp línea ~81:
        int pts = open(devname, O_RDWR);
        if (pts < 0) exit(-1);  // exit(-1) → WEXITSTATUS=255
      Si el slave PTY no puede abrirse (SELinux, permisos, /dev/pts no montado),
      el proceso hijo termina con exit(-1)=255 antes siquiera de ejecutar PRoot.
    * Solución aplicada en esta ronda:
      - Se añadió logging nativo vía __android_log_print en termux.cpp para
        distinguir entre fallo de PTY slave (exit -1) y fallo de PRoot.
      - PROOT_TMP_DIR corregido a "/tmp" (guest-relative) en lugar del path host.
      - Se añadió logging detallado en TerminalSession.initializeEmulator()
        para registrar args/env exactos.
      - DebugLogger ahora auto-adjunta sessionId y pid a todos los logs.
      - DiagnosticPipeline.postLog() integrado en session lifecycle.
    * Pendiente: Revisar logs nativos tras aplicar estos cambios para
      determinar la causa raíz exacta. Posibles causas:
      a) open(devname) falla → SELinux o /dev/pts no accesible.
      b) PRoot falla con 255 por PROOT_TMP_DIR o seccomp.
      c) /bin/sh no existe o no es ejecutable en el rootfs descargado.
    * Recomendación LD_PRELOAD (postergada hasta resolver exit 255):
      a) Añadir bind mount de /system/bin/linker64 en PRoot args.
      b) Modificar termux_exec.cpp para detectar PRoot.
      c) Cargar LD_PRELOAD desde perfil de shell.
